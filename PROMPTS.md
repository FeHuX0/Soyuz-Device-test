# Промпты и принятые решения

Точный исполняемый текст `SYSTEM_PROMPT`, `USER_TEMPLATE` и их сборка находятся только в [src/prompts.py](src/prompts.py). Эта документация описывает решения; отдельной копии инструкций здесь нет, чтобы версии не расходились.

## System

Роль — технический редактор B2B-магазина КИП. Правила требуют спокойного делового русского текста, запрещают SEO-переспам, неподтверждённые преимущества и восстановление характеристик из знаний модели. Числа, единицы, стандарты, сертификаты, материалы, гарантии и условия применения разрешены только при наличии в источнике. Все исходные пары `specs` сохраняются дословно, пропуски обозначаются «данных нет», неоднозначности — в `warnings`.

Длина описания задана и в инструкции, и в схеме. При недостатке фактов предлагается пояснить вопросы для подбора, а не выдумывать свойства для достижения длины. `temperature=0.1` уменьшает вариативность; это не гарантия фактической точности.

## User и недоверенные данные

Товар сериализуется в JSON и помещается в `<product_data>`. Исходное описание не подставляется в system и не получает отдельной роли. Символы угловых скобок внутри JSON экранируются, поэтому строка с закрывающим тегом не создаёт новый блок. System прямо трактует весь товар, включая `description`, как данные и запрещает исполнять содержащиеся там команды.

Рядом передаются отдельные списки пропусков и предупреждений, вычисленные кодом до вызова API. Модель может дополнять их, но постобработка гарантированно возвращает исходные пункты. Экранирование не является полной защитой от prompt injection; редакторская проверка сохраняется.

## Схема и защита от галлюцинаций

`ProductCard` передаётся instructor непосредственно как `response_model`. `Field(description=...)` у каждого выходного поля объясняет ожидаемое содержание. Pydantic проверяет длины заголовка и описания, количество запросов, вложенные `SpecItem`, строгие типы и отсутствие лишних полей.

`model_validator` получает исходный `ProductInput` и рассчитанные пропуски через контекст валидации. Без контекста карточка не считается валидной. В закреплённой версии instructor 1.17 внешнее имя аргумента — `context`; парсер передаёт его как `validation_context` в обработку Pydantic, где он доступен в `ValidationInfo.context`.

Проверка требует сохранить все непустые пары `specs` с исходными именами и значениями; запрещает новые пары, дубли и перенос значения к другой характеристике. Только для вычисленных пропусков разрешено «данных нет». В описании, заголовке, блоке менеджера и запросах каждое число сверяется с источником; сочетания числа и единицы сверяются целиком, поэтому наличие `100 мм` и отдельного числа из диапазона не разрешает приписать `100 бар`. Нормализуются пробелы, регистр, тире и десятичный разделитель. Известные идентификаторы модели исключаются из выделения единиц, но их числа проверяются.

Это консервативная лексическая проверка, а не доказательство смысла. Она не обнаружит все ложные утверждения словами и не гарантирует смысловую привязку числа к параметру внутри свободного текста. Эти границы явно указаны в README.

## Почему instructor

Нужны не только JSON-парсинг и описание полей, но и повторный запрос с конкретной ошибкой пользовательского Pydantic-валидатора. Instructor объединяет схему, контекст и автоматическую обратную связь модели. Используется `from_openai` в режиме tool calling, `max_retries=2`; собственного цикла для исправления ответа нет.

После исчерпания валидационных повторов сервис ловит `InstructorRetryException`, возвращает понятную ошибку и только содержимое последней попытки, если оно доступно. Эта попытка помечена предупреждением и не выдаётся за проверенную карточку.

Транспортная политика отдельная: OpenAI SDK получает `max_retries=2` и на временных ошибках применяет свой backoff с jitter. Instructor не перезапускает исчерпанные транспортные повторы. Вложенную ошибку SDK сервис распознаёт отдельно от ошибки валидации. Это проверяется HTTP-заглушками, включая постоянные 429/5xx/таймауты и восстановление после 429. См. [политику повторов instructor](https://python.useinstructor.com/concepts/retrying/).

Результат сохраняется только после успешной проверки. Для Markdown используется один рендерер, а JSON и Markdown в форме получаются из одной и той же проверенной модели, без второго обращения к LLM.
