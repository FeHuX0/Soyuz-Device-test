# AI-помощник для подготовки карточек КИП

Локальный MVP: принимает JSON о приборе, через OpenAI и instructor готовит русский черновик карточки. Один пайплайн обслуживает CLI и FastAPI с простой HTML-формой. Результат доступен в JSON и Markdown. Требуется проверка контент-менеджером.

## Установка

1. Установите **uv**: [инструкция Astral](https://docs.astral.sh/uv/getting-started/installation/).

   Linux / macOS / Git Bash:

   ```sh
   curl -LsSf https://astral.sh/uv/install.sh | sh
   ```

   Windows PowerShell:

   ```powershell
   powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
   ```

   Откройте новый терминал, если `uv` ещё не находится в PATH.

2. В корне скачанного или клонированного репозитория выполните:

   ```sh
   uv sync
   ```

   uv сам подготовит Python 3.11 и `.venv`, установит зависимости из `uv.lock`, включая dev-группу. Ручное создание и активация окружения не нужны. Проект создан командой `uv init --app --no-package --python 3.11`, в `pyproject.toml` явно задано `package = false`.

3. Скопируйте `.env.example` в `.env` и заполните `OPENAI_API_KEY`. На Windows можно использовать `Copy-Item .env.example .env`, в Unix — `cp .env.example .env`. Настоящий ключ в репозиторий не добавляйте.

   | Переменная | Значение по умолчанию | Назначение |
   | --- | --- | --- |
   | `OPENAI_API_KEY` | отсутствует | Обязательный секрет для генерации |
   | `OPENAI_MODEL` | `gpt-4.1-mini` | Модель с tool calling и поддержкой `temperature` |
   | `OPENAI_TIMEOUT` | `30` | Таймаут одного HTTP-запроса, секунды, больше нуля и не больше 300 |

   Переменные процесса имеют приоритет над `.env`. Ключ загружается только на сервере; форма работает и без него, генерация вернёт понятную ошибку. Повторы могут увеличить общее время ожидания сверх `OPENAI_TIMEOUT`.

   Выбрана модель `gpt-4.1-mini` с `temperature=0.1`. У модели объявлено прекращение обслуживания 14 января 2027 года: перед дальнейшим использованием проверьте доступность и обновите `OPENAI_MODEL` на совместимую модель. См. [официальную страницу модели](https://developers.openai.com/api/docs/models/gpt-4.1-mini) и [Chat Completions API](https://developers.openai.com/api/reference/python/resources/chat/subresources/completions/methods/create). Доступ конкретного аккаунта без рабочего ключа не проверялся.

## CLI

```sh
uv run python -m src.cli examples/product_1.json
uv run python -m src.cli examples/product_2.json --format markdown
```

Сохранение результата в UTF-8 без зависимости от кодировки перенаправления в PowerShell:

```sh
uv run python -m src.cli examples/product_1.json --output examples/output/product_1.json
uv run python -m src.cli examples/product_1.json --format markdown --output examples/output/product_1.md
uv run python -m src.cli examples/product_2.json --output examples/output/product_2.json
uv run python -m src.cli examples/product_2.json --format markdown --output examples/output/product_2.md
```

Каждый запуск генерации — отдельное обращение к сервису. Для двух форматов одного и того же ответа используйте веб-форму или HTTP с `format=both`. Без `--output` результат печатается в stdout. Ожидаемые ошибки выводятся JSON-объектом в stderr, код завершения — `1`; успешный запуск — `0`. Неуспешный запрос не записывает карточку в выходной файл.

## Веб-форма и HTTP

```sh
uv run uvicorn src.api:app --reload
```

Откройте <http://127.0.0.1:8000>. Вставьте JSON, нажмите «Подготовить черновик». Кнопки «Копировать JSON» и «Копировать Markdown» копируют два представления **одного** ответа, без повторной генерации. При исчерпании попыток последняя версия показывается отдельно как не прошедшая проверку. Буфер обмена рассчитан на localhost; при запрете браузера доступно ручное копирование.

HTTP: `POST /api/generate` с JSON-телом. Доступны:

- `?format=json` (по умолчанию): непосредственно `ProductCard`;
- `?format=markdown`: текст Markdown;
- `?format=both`: объект `{"card": ProductCard, "markdown": "..."}`.

Ответы с ошибками всегда JSON: `error`, `code`, при наличии — `missing_fields`, `warnings`, `last_attempt`. Статусы: `422` — входные данные, `429` — лимит/квота, `504` — таймаут, `503` — конфигурация/недоступность провайдера, `502` — отклонённый запрос или невалидный ответ. Неожиданные ошибки возвращают общее сообщение с `500`, без traceback. `last_attempt` — строка с непроверенным содержимым модели, она не является `ProductCard`.

## Вход

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Все значения и ключи характеристик — строки; `specs` — объект. Пропущенные поля и пустые строки допустимы и отмечаются в `missing_fields`. Числа, `null`, массивы вместо объектов, неизвестные поля, дубли ключей и невалидный JSON отклоняются **до** загрузки клиента. Пробелы по краям строк удаляются. Полностью пустой товар не вызывает LLM. Товар с названием и пустым `specs` допустим как неполный.

## Выход

| Поле | Содержание |
| --- | --- |
| `seo_title` | Русский заголовок, до 70 символов |
| `seo_description` | Русское описание, 800–1200 символов |
| `key_specs` | Список объектов `{"name": "...", "value": "..."}` |
| `search_queries` | 3–5 непустых разных запросов |
| `manager_block` | Кому подходит прибор и какую задачу решает |
| `missing_fields` | Пропуски и вопросы для уточнения |
| `warnings` | Неоднозначности и сомнения в исходных данных |

Названия JSON-полей служебные, содержимое — на русском; исходные обозначения моделей и единиц сохраняются. `ProductCard` — Pydantic-схема и `response_model` instructor. Её валидатор получает исходный товар через контекст. В instructor 1.17 аргумент называется `context`; внутри разбора он передаётся в Pydantic как `validation_context` и доступен в `ValidationInfo.context`. Это соответствует проверке по исходным данным из ТЗ. Версии instructor и SDK ограничены в `pyproject.toml` и зафиксированы в `uv.lock`.

## Примеры и статус реальной генерации

- `examples/product_1.json`: исходный пример DM 02 из PDF, все приведённые характеристики сохранены; описание в самом PDF краткое и заканчивается многоточием.
- `examples/product_2.json`: иллюстративный термопреобразователь с неизвестным производителем, диапазоном и точностью. Свойства реальной модели не восстанавливаются по её обозначению.
- `examples/invalid_json.json`: синтаксическая ошибка, API вызываться не должен.
- `examples/empty_specs.json`: допустимый неполный вход; показывает предупреждения и необходимость уточнений.

При подготовке прототипа **OPENAI_API_KEY отсутствовал**. Оба основных примера были переданы сервису, который вернул `configuration_error`. В `examples/output/*.error.json` сохранена фактическая диагностика. Успешные карточки `.json`/`.md` не сгенерированы и не подделаны. После настройки ключа выполните команды сохранения выше. Тексты в тестовых фикстурах — только заглушки для автоматических проверок.

## Проверки

```sh
uv run pytest
uv run ruff check .
```

Тесты не требуют ключа и не обращаются в сеть. Они проверяют строгий вход, пропуски, границы схемы, неподтверждённые значения/единицы, реальные валидационные повторы instructor, раздельный backoff SDK, ошибки, CLI, HTTP и Markdown. Для тестов транспорта используется dev-зависимость `httpx2`, соответствующая выбранному OpenAI SDK.

Для проверки воспроизводимости из чистого клона выполните `uv sync`, затем указанные команды тестов, линтера, CLI и веба. Отсутствующий ключ должен приводить к понятному сообщению, а не мешать запуску формы и тестов.

## Принятые допущения

- Отсутствующие поля не делают частичный товар автоматически невалидным. Для генерации достаточно любого непустого исходного значения; результат с недостатком данных требует уточнения.
- Произвольный словарь `specs` не задаёт обязательные характеристики для всех типов приборов. В коде принят минимальный список вопросов для подбора: диапазон и точность/погрешность. Они распознаются по русским ключам; отсутствие означает необходимость уточнения. Дополнительные вопросы может предложить модель.
- Короткое описание — менее 80 символов — вызывает предупреждение, но не блокирует запрос.
- Все непустые пары `specs` копируются дословно. Пропуски характеристик добавляются как «данных нет» в постобработке, если модель их опустила. Пропуски и предупреждения, рассчитанные кодом, всегда сохраняются.
- SDK выполняет до двух транспортных повторов с backoff для временных ошибок. `max_retries=2` у instructor задаёт отдельно два повтора при ошибке структурирования/валидации. Собственного цикла валидационных ретраев нет.
- Приложение рассчитано на локальное использование; хранение данных, CMS, БД, админка и деплой не реализованы.

## Ограничения и возможные улучшения

- Проверка чисел и сочетаний «значение + единица» лексическая: регистр, десятичный разделитель, пробелы и тире нормализуются, пересчёт единиц запрещён. Необычные обозначения могут вызывать консервативные отказы. Идентификаторы моделей из названия обрабатываются отдельно, чтобы слово после DM 02 не считалось единицей.
- Точная проверка пар защищает `key_specs`, но текстовый валидатор не доказывает смысловую корректность всех фраз, принадлежность каждого числа конкретной характеристике и отсутствие утверждений словами. Материалы, стандарты и назначение в тексте дополнительно ограничены промптом и требуют проверки редактором.
- Изоляция товарных данных и экранирование тегов снижают риск prompt injection, но не дают абсолютной защиты от влияния недоверенного описания.
- При скудном входе требование 800–1200 символов может дать больше пояснений о недостающих данных или отказ после повторов. Длину код не добивает шаблонным текстом.
- Проверка противоречий описания и характеристик поручена модели. Следующее практическое улучшение — согласованные с каталогом правила характеристик по категориям и проверка на реальных паспортах приборов.
- Реальное качество русского текста, доступность модели в аккаунте и ручная проверка интерфейса в браузере без рабочего API-ключа не подтверждены. Автоматические проверки не заменяют эти этапы.
